The four small phases ran sequentially in one stream; evolution ran in a
second stream in parallel. The near-zero losses are overfitting on tiny
datasets, not evidence of quality — the golden scores below are the real
signal. Each adapter has its own `models/<phase>/2026-10-26-cpu-v3/`
(manifest + checkpoints + 24 MB weights). Nothing was merged to GGUF and no
adapter is loaded by the runtime: Phantom still runs the deterministic
engine.

## 2. Golden-set evaluation (3 rows per phase)

```
python -m training.predict --phase <p> --adapter models/<p>/2026-10-26-cpu-v3/adapter \
    --base-model training/base/Qwen2.5-0.5B-Instruct --out training/eval/v3/<p>.pred.jsonl
python -m training.eval --phase <p> --predictions ... --out training/eval/v3/<p>.json
```

The deterministic heuristic was scored on the same rows for a baseline.

| phase | metric | adapter | baseline | gate |
| --- | --- | --- | --- | --- |
| exploit | ndcg | 0.5068 | 0.9065 | **not promoted** |
| finding | exact_match | 0.6667 | 1.0000 | **not promoted** |
| osint | brier | 0.9625 | 0.9775 | **not promoted** |
| social | rubric | — | — | not measured |
| scan_parse | exact_match | 0.6667 | 1.0000 | **not promoted** |
| evolution | exact_match | 1.0000 | 1.0000 | promoted (tie) |

Honest reading:

- **exploit** — the training labels only ever rank **one** candidate
  (`ranked` length is always 1), while the golden set asks for an order of
  2–3. The model learned the schema and returns one id; the short ranking
  loses NDCG. This is a dataset defect, not an epoch count: more training
  would memorise the single-candidate shape harder.
- **finding** — 2/3 exact. `finding-2` expects `kind: "web_anomaly"`, which
  is **not** in the runtime `FINDING_KINDS`; the schema-valid answer
  (`vuln_class`) is scored 0. The golden fixture needs the builder's kind
  mapping (`web_anomaly → hunt_anomaly`) before this metric means anything.
- **osint** — one exact hit, two confidence misses (0.0 vs 0.15, 0.85 vs
  0.55). Brier 0.9625 vs 0.9775.
- **scan_parse** — the model added port 80 that the nmap output does not
  contain (`Not shown: 998 filtered`); the deterministic parser was exact on
  all three. A real hallucination, not a converter bug.
- **social** — no rubric was supplied, so `training.eval` reports 0 by
  design. The manifest keeps `eval` empty and `promoted: false`: an
  unmeasured model must not be loaded.
- **evolution** — exact on all three; this ties the heuristic, it does not
  beat it, and 3 rows are not a production gate.

Manifests were updated with the measured metric and the baseline
(`promoted` derived by `training.manifest`). Five of six are correctly
refused for being below baseline or unmeasured.

   the heuristic itself.

   model.

   (the current 3 rows are a smoke test).
5. A34: rerun when a service is actually listening; the host already
   answers ARP, so the network path is fine.

### AUTO-MODE (300 s bound each, `--stealth --exploit-all --ai off`)

Both targets were refused at first because **no scope was declared**:

```
[✘] ERROR: no engagement scope and 1 network target(s), so auto-mode
    refuses every remote target ... declare the authorized range with
    `scope add <cidr>` ... PHANTOM_ALLOW_UNSCOPED=1 for a lab/CTF
```

With the documented lab exception the runs started (C2 listener on :8080,
HTTPS/mTLS) and behaved as follows on both hosts:

1. full-range `scan_tcp` (`-p 1-65535 -T2 --min-rate 500 --host-timeout 200s`)
   timed out; result marked `Unverified: no declared effect`;
2. `version_detect` refused (`no open services known yet`);
3. `curl_probe` on 21/22/25/80/443 failed, marked unverified;
4. `recon_ladder` verdict `unreachable`;
5. recovery re-armed the ladder and started the full scan again;
6. the 300 s external bound ended both runs (`EXIT=124`).

The engine never invented an open port or a compromise. **But the first
run was too slow to be useful**: the full scan used `-T2 --min-rate 500`
and hit `--host-timeout 200s` without returning, so AUTO-MODE never saw
5040/5357.

**Fixed the same day** in `phantom/automation/guidance/kit.py`:

- full-range timing is now `-T3 --min-rate 1000` for `--stealth` (and
  `-T4 --min-rate 1500` for balanced), plus `-n` to skip reverse DNS;
- the same command on the same host completes in **41 s** and prints
  `5040/tcp open`, `5357/tcp open`;
- a non-timeout nmap failure now salvages the ports it already printed
  (`phantom/automation/agent.py`), instead of discarding the output.

Re-run with the fix: AUTO-MODE finished in **1m 04s**, `services=2`,
`actions_taken=2`, wrote raw/client reports and a checkpoint, and
`exploit-all` reported `no actionable CVE ... nothing was executed`.
`tests/test_network_policy.py` was updated to the new bounded timing
(71 network/auto tests pass).

### Trained model in the runtime path

The merge was real: `training.export` produced
`models/evolution/2026-10-26-cpu-v3/merged` (958 MB), served through a
minimal OpenAI-compatible endpoint on :8089. With
`PHANTOM_AI_MODE=integrated`:

- `ModelRegistry().promoted("evolution")` returns `2026-10-26-cpu-v3`;
- `promoted("exploit")` returns `None` (below baseline, correctly refused);
- the evolution advisor fell back to deterministic because the model's
  answer carried an extra `details` key:
  `{'source': 'deterministic', 'error': 'unknown keys: details'}`.

So the gate works (invalid JSON is refused, the deterministic path
continues), but this 0.5B adapter is **not** production quality yet: it
knows the shape but adds one key. No GGUF was produced, and Phantom does
not ship the Qwen base model: `ai.mode` defaults to `off`, and
`local`/`integrated` talk to an OpenAI-compatible server whose URL/model
must be configured (`ai.local.base_url`, `ai.local.model`,
`PHANTOM_AI_LOCAL_URL`, `PHANTOM_AI_LOCAL_MODEL`).
