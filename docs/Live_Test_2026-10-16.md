## 3. Defects found (all reproduced today)

### D1 — `/api/c2/artifacts` returns 500 on every call (backend)

```
phantom/api/server.py:212   from phantom.core.artifact_policy import classify as artifact_class, ...
phantom/api/server.py:241   "class": (artifact_class(subdir, name)),
phantom/core/artifact_policy.py:94   def classify(subdir: str) -> Dict[str, Any]:
```

`TypeError: classify() takes 1 positional argument but 2 were given`. The
traceback appears in the API log on **every poll the UI makes** while the C2
Dashboard is open. Beyond the mismatch, the call is semantically wrong:
`artifact_policy.classify` classifies a *directory* and returns a metadata dict,
while the call site wants a per-file class string.

*Fix:* classify by directory once per `subdir` and read the class name from the
returned dict (or add a `classify_file(subdir, name)`), then re-run
`tests/test_api.py`. *Impact:* the governance metadata the endpoint exists for
(class + TTL per artefact) has never been served; the UI sees an error payload.

### D2 — `POST /api/network/scan` ignores a bare-IP `target` and sweeps the whole subnet (scope)

```
phantom/core/netmap.py:465   cache_key = target or "<local>"
phantom/core/netmap.py:470   if target and "/" in target:   cidrs = [ip_network(target)]
phantom/core/netmap.py:476   else:                          cidrs = _local_cidrs()
```

Measured: `{"target": "192.168.1.6"}` returned the **full** local sweep (10 hosts
including the gateway) at `08:31:27`; `{"target": "192.168.1.18"}` did the same
at `08:31:38` (9 hosts). `{"target": "192.168.1.18/32"}` honoured the scope
(`0 hosts`, `method: none`, 0.5 s). So an operator who scopes a scan to one host
silently scans the entire network instead — the opposite of what a scope control
is for, and exactly the kind of thing that lands an engagement outside its
authorization.

*Fix:* treat a bare IP as `/32` (`ip_network(target + "/32")` for
`ipaddress.ip_address()`-parseable input) and return an explicit error for
anything else. *Impact:* scope violation risk; also wasted traffic.

### D3 — the UI reports two different versions of itself

```
electron/src/components/Sidebar.tsx:141     v3.7.3 · Electron
electron/src/components/SettingsPanel.tsx:530   3.7.3
electron/src/App.tsx:165                    v3.0.0
phantom/core/c2_shell.py:84, :746           v3.0.0      (hardcoded strings)
electron/package.json                       3.0.0
```

Same screen: the status bar says 3.7.3 while the header says v3.0.0. A stale
`Phantom-3.7.3-win-x64.exe` in `dist-release/` suggests where 3.7.3 came from.

*Fix:* one source of truth (package.json / `phantom.__version__`) injected at
build time; drop the literals. *Impact:* release provenance, bug reports,
"which build am I running" — currently unanswerable from the UI.

### D4 — "Scan Network" gives no feedback once the map has data (UI)

```
electron/src/components/NetworkMap.tsx:213   const [scanMsg, setScanMsg] = useState('')
electron/src/components/NetworkMap.tsx:300   {scanMsg && <p ...>{scanMsg}</p>}
```

Line 300 lives inside the `if (!data || data.nodes.length === 0)` branch, so the
message is rendered **only on the empty state**. Verified live: after a
successful scan (store mtime moved, §P2) the document contained neither
`Found … device(s)` nor `Scan failed`, and the button had already returned to
its idle label. Related: the renderer's generic bridge races every call at 15 s
(`FAST_MS` in `electron/src/lib/api.ts`), and the scan is a `POST` that runs a
full sweep (7.8 s here, more on a slow/quiet network) — so on a slow network the
call can be cut at 15 s and the *only* signal would be the message that is never
shown.

*Fix:* render the status line in both branches (and give the scan a longer
timeout, as `/api/automode/run` already does). *Impact:* an operator cannot tell
a completed scan from a failed one from a hung one.

## 5. Blockers and prerequisites

### 5.1 The two named targets are not reachable right now

| Target | ARP | ping | mapper | in host store |
| --- | --- | --- | --- | --- |
| `192.168.1.6` (A34) | present `62:eb:35:3e:74:17` | 2/2 lost on retest | alive at `08:31:27` once, then absent | **yes** — `A34-di-cristian`, `alive: true`, `last_seen 08:31:27` |
| `192.168.1.18` (HP) | present `38:d5:7a:a8:c9:f5` | 2/2 lost, both attempts | `/32` scan → 0 hosts, `method: none`, 0.5 s | **no** — never discovered |

Both are visible at layer 2 (the router has them in ARP) but neither answers
ICMP, which is the only discovery primitive available on this box today. The
phone answered *once* — an Android in doze — then went quiet; the PC never did.
**Both must be awake and answering before any of the phase-2 work can start**;
if the PC keeps dropping ICMP, discovery needs `nmap`/`arp-scan` present (the
Kali/WSL bridge is one option) or the device needs to be woken.

### 5.2 No breach source is configured

`phantom/automation/social/engine.py:449-459` requires `PHANTOM_HIBP_API_KEY`
(HaveIBeenPwned v3) or `PHANTOM_BREACH_API`; without one it returns
`no breach source configured`. Checked: not in the shell environment, not in
`phantom_state.json`, and `.env` carries `AI_*`, `PHANTOM_C2_*`,
`PHANTOM_PAYLOAD_TOKEN`, `PHANTOM_API_TOKEN`, `NVD_API_KEY`,
`PHANTOM_TELEGRAM_*` — **no HIBP/breach key**. So the breach half of the identity
test cannot run until a key exists, and the operator has to supply it.

### 5.3 There is no remote path to a phone in this framework

Worth stating plainly, because it decides the mobile phase: the mobile attacker
model in the framework (`--profile mobile`, OS sandbox / MDM / carrier SMS
filtering) and the code base itself route mobile delivery through the
**social-engineering kit** (`social/aitm.py`, `attachment.py`, `mailers.py`,
`social_dm.py`, `spoof.py`, `templates.py`) or a **manual APK install**. There
is no remote exploit in the tree that lands a beacon on a modern Android handset,
and the installer-level permissions (camera, mic, location) are granted by the
person holding the phone, not by the tool. The operator has ruled the social
path out for this session, so a beacon on the A34 is not reachable in this
configuration — that is a property of the framework, not a missing step.
