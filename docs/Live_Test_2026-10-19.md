## 1. Defects found live and fixed

### 1.1 `migrate` could not fetch its PIC payload (403, 29 bytes)

* Symptom: `migrate` → `MIGRATE_ERROR: failed to fetch PIC payload from C2
  (29 bytes)` on `B-9C32F6E83BCBAE0E` (build `4f4fb144`). 29 bytes is the
  `Forbidden: Invalid auth token` body of `/x`.
* Root cause: `/x` authorises through the PER-BEACON download token derived
  from `X-Beacon-Id` (`_payload_token_ok` → `get_beacon_download_tokens`).
  The argument-less migrate called `http_request(cfg, GET, "/x", "", "")` —
  the 5th argument is the beacon identity and it was empty, so the request
  carried no `X-Beacon-Id` and the server could not resolve the token.
  Server-side proof: the same derived token + `X-Beacon-Id: B-…` returns
  **200 / 1,613,848 bytes**; without the header **403 / 29 bytes**.
* Fix: pass `cfg.beacon_id` (same shape persistence strategy 2 already used
  after its own 403 fix earlier in the cycle).
* Evidence after fix (`B-296B2B8DEF9002B0`):
  `migrate | Migrated successfully (PPID spoofed) to PID 28808
  (parent: explorer.exe) (self-migrated from C2 PIC payload)`, followed 29 s
  later by `health | uptime_s=25 checkins_ok=6 …` — the successor instance
  answering from inside `RuntimeBroker.exe` (PID 28808).

### 1.2 Self-migration left NOTHING alive (successor killed itself)

* Symptom: first fixed build (`B-98103F027925BE24`) reported
  `Migrated successfully … to PID 28304`, then the beacon never answered
  again — host PID gone, `health` → `NO_RESULT`.
* Root cause: the single-instance guard (`CreateMutexA(…, TRUE, mux)` +
  `ERROR_ALREADY_EXISTS` → return) runs at beacon start. Migration spawns the
  successor while the ORIGINAL instance is still alive (it must still send the
  result and tear down), so the successor saw the mutex held and exited within
  milliseconds; the original then exited on the `\x01\x02MG` sentinel. Net
  effect: zero beacons.
* Fix: the guard now creates the mutex WITHOUT initial ownership and
  `WaitForSingleObject(hMux, 30000)`. The successor waits out the old owner;
  when the old process dies the kernel marks the mutex abandoned and the
  successor takes over (`WAIT_ABANDONED`). A genuine duplicate (RunKey rebirth
  while the senior lives) times out and yields to the senior instance.
* Evidence after fix: `B-296B2B8DEF9002B0` health from the migrated instance
  (above); the migrated process was confirmed as `RuntimeBroker` PID 28808,
  started at the migrate timestamp, parent `explorer.exe`.

### 1.3 `remote` deploy: fetch failed 401 (12 bytes)

* Symptom: `REMOTE_ERROR: module binary unavailable 12`. 12 bytes =
  `Unauthorized`.
* Root cause: the handler built the URL as
  `/api/v1/remote_payload_windows?auth=<payload_token>`. The per-beacon HMAC
  signature is computed over the path **including the query**, but the server
  verifies over aiohttp's `request.path`, which **excludes** the query — so
  every such request failed the auth middleware before `_payload_token_ok`
  ran. Additionally `wants_payload_token()` did not match
  `/api/v1/remote_payload*`, so no `X-Auth-Token` header was sent either.
* Fix: the fetch path carries no query (`/api/v1/remote_payload_windows`,
  `_linux`, `_android`); the per-beacon token travels in `X-Auth-Token`
  (`wants_payload_token()` now matches `/api/v1/remote_payload`), and both
  http_request twins (WinHTTP + libcurl) strip any query before signing.
  The failure string now echoes the server body instead of a bare byte count.
* Evidence after fix: direct route check with the beacon's derived token +
  `X-Beacon-Id` → **200 / 1,051,136 bytes `MZ…` (remote.exe)**; beacon-side
  `remote` moved past the fetch to `REMOTE_ERROR: spawn failed`.
* Residual (environment, not code): McAfee refuses to EXECUTE the fetched
  module — a manual `Start-Process` of `remote.exe` is rejected with "the file
  contains a virus or potentially unwanted software" (quarantine DB updated at
  that minute). The download path is verified; the spawn is blocked by the lab
  AV exactly like persistence strategy 2.

### 1.4 Linux persistence: systemd unit silently never installed

* Symptom: on Kali, `persist` reported only `[autostart]` and `[cron]`; the
  unit file `~/.config/systemd/user/PhantomBeacon.service` did not exist.
* Root cause: `establish_linux` used a single-level `mkdir()` on
  `~/.config/systemd/user`; when the parents did not exist yet the directory
  creation failed silently and the unit write then failed too (graceful
  degradation hid a dead persistence arm).
* Fix: recursive `mkdir_p()` used for every directory the Linux arm creates.
* Evidence after fix (`B-ED33508375324071`, Kali):
  `persist | … [systemd] /home/kali/.config/systemd/user/PhantomBeacon.service
  [autostart] … [cron] Every 10 minutes`, unit file present and well formed,
  `systemctl --user is-enabled` → `enabled`, `is-active` → `active` (the
  service started a second instance from `~/.local/bin/phantom_beacon`, as a
  service restart should). `unpersist` → service `not-found`/`inactive`, all
  files removed, duplicate process gone, original `/tmp` instance untouched.

### 1.5 Linux `netinfo` returned an empty string

* Symptom: `netinfo` on Kali produced zero bytes while `netstat`, `sysinfo`
  and `drives` all answered — the Windows build's `netinfo` is rich.
* Root cause: the whole body of `recon::get_netinfo()` lived under
  `#ifdef _WIN32`; the POSIX side fell through to `return out;` with `out`
  empty.
* Fix: a `__linux__` branch using `getifaddrs` (IF / MAC / IPv4 / IPv6, with
  AF_PACKET for link addresses), plus default gateway from `/proc/net/route`
  and resolvers from `/etc/resolv.conf`, mirroring the Windows output shape.
  Other POSIX platforms keep the previous behaviour (no untested claim).
