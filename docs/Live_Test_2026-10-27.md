## 1. Auto-mode fired no weapon while the manual core confirmed one

Measured first, then fixed. Same host, same port, same day:

| path | CVE-2021-41773 on 127.0.0.1:8081 |
| --- | --- |
| manual core `fire` | `VULNERABLE via poc (VULNERABLE (traversal))` |
| auto-mode `--exploit-all` | `no actionable CVE in the WorldModel` |

Cause (not a hypothesis): `version_detect` declares the `service` fact — the
very fact the scan just produced — so nothing was missing and the planner
never asked for it. Every service reached the sweep with `product` and
`version` empty, and the CVE registry matches on exactly those two fields, so
the candidate list was structurally empty. The scan even labelled 8081
`blackice-icecap`, the label for a *filtered* port.

Fix — `phantom/core/automode.py::_fingerprint_before_exploit`: one bounded
`version_detect` over the ports the run already proved open, through the same
gates as any other capability, run BEFORE the sweep ranks anything. It is a
no-op when every service is versioned, and a refusal (recon banned for this
worker, no nmap, gate veto) is reported in the sweep summary instead of
vanishing. The "no actionable CVE" receipt now names the ports that stayed
blind, so "no weapon" and "no fingerprint to match a weapon against" no longer
read the same.

Re-run on the lab, `--stealth --exploit-all --ai off`:

```
exploit-all: version fingerprint before the CVE match — 6 of 29 unversioned service(s) now carry a product/version
exploit-all: 1 execution(s), 1 confirmed vulnerable, 0 RCE
exploit-all: 127.0.0.1:6379 vulnerable via non_cve (... redis_version:7.4.11 ...)
```

With `--exhaustive` (lab/debug: consider every candidate):

```
exploit-all: version fingerprint before the CVE match — 6 of 29 unversioned service(s) now carry a product/version
exploit-all: 4 execution(s), 3 confirmed vulnerable, 0 RCE
exploit-all: 127.0.0.1:6379 vulnerable via non_cve
exploit-all: 127.0.0.1:2375 vulnerable via non_cve
exploit-all: CVE-2021-41773 via msf - no session opened
exploit-all: CVE-2021-41773 vulnerable via poc (VULNERABLE (traversal))
```

So the chain is complete in auto-mode. In the default best-path mode the sweep
still stops at the *best* path, and on this lab that is Redis: 86.0 vs 66.9 in
stealth (unauthenticated Redis control, complexity 0.10, noise 0.20, against a
CVE at complexity 0.45, noise 0.58). That is the documented "best + one
fallback" semantics, not a broken chain — `--exhaustive` is how a lab run
reaches the CVE, and the ranking is printed so the choice can be audited.

## 2. The manual shell could not be scripted at all

`use scan` + `run` with a piped stdin died with
`Failed to enter module scan: EOF when reading a line`: the preview reached
`input()` with no terminal. Every end-to-end test (and any CI) was impossible.

Fixed in `phantom/core/preview.py` + the three `_execute_flow`s:

- `PreviewSession.choose()` — the menu when a terminal is attached, the
  module's own first group when stdin is a pipe, and the line says so;
- `input()` raising `EOFError` mid-menu now degrades the same way instead of
  printing a traceback;
- `run-group <name>` is now a module command, not only an entry inside the
  interactive menu, and `run --group <name>` selects one group without a menu.

Live, piped, no TTY:

```
$ printf 'set target 127.0.0.1\nset scope 127.0.0.1\nuse scan\nrun\nexit\n' | python -m phantom.main --manual
  stdin is not a terminal: no menu to answer — running the first group
  'SUGGESTED (First Steps)'. Ask for another with `run-group <name>`
  (available: SUGGESTED (First Steps), NMAP (Basic), ...) or `run-all`.
```

and the manual payload chain on the same lab:

```
$ printf '...\nuse exploit\nfire CVE-2021-41773 --port 8081\nexit\n' | python -m phantom.main --manual
[*] Firing CVE-2021-41773 on 127.0.0.1:8081 via local PoC...
[✔] CVE-2021-41773: VULNERABLE via poc (VULNERABLE (traversal))
```

## 3. Two scan rows that reported a healthy host as dead

Both measured on the lab, not inferred:

| command | result on 127.0.0.1:8081 |
| --- | --- |
| `nmap -sV -sC -p 8081` | `Note: Host seems down` (no ports at all) |
| `nmap -Pn -sV -sC -p 8081` | `8081/tcp filtered blackice-icecap` |
| `nmap -Pn -sS -p 6379,8081` | both **filtered** |
| `nmap -Pn -sT -p 6379,8081` | both **open** |

1. **No `-Pn`.** The recommended first steps probed with ICMP/host discovery
   first, so on any host that drops ping (this Windows box, and the LAN host in
   the 2026-10-26 notes) the operator read "Host seems down" as "no services".
   `SUGGESTED (First Steps)` and `SUGGESTED (Follow-up)` and the `NMAP (Basic)`
   rows now carry `-Pn`.
2. **No connect-scan row.** A SYN probe comes back *filtered* through a port
   forwarder or WSL loopback while the connect scan opens the same ports.
   `NMAP (Basic)` gained `-Pn -sT -sV -sC -p- -oX` (same port space, same XML,
   so it still feeds the exploit module) as the row to use when SYN is
   filtered.

On the real LAN host both scan types agree (`5357/tcp open wsdapi` with `-sS`
and with `-sT`), so this is a loopback/forwarded-target row, not a replacement.

## 5. ML: dataset defects that made two phases unmeasurable

### exploit — the labels could not teach an order

The builder labelled every step with exactly ONE id (the capability the run
happened to pick), while the golden set asks for an ordering. Measured
2026-10-26: adapter NDCG 0.5068 against a heuristic that returns the whole
table (0.9065) — unwinnable, and more epochs would only memorise the
single-candidate shape.

`training/build_dataset.py` now emits, per executed step: the run's real
candidate table (executed actions + the planner's pending hypotheses) and a
graded tail ordered by what the RUN established — an executed action that
worked, then the planner's pending hypotheses by priority, then what already
failed. The run's own decision stays first.

```
rebuild: exploit 113 record(s); ranked lists >1 id: 105/113, max 9, mean 5.79
```

### finding — the golden datum, not the model, was wrong

`finding-2` expected `kind: "web_anomaly"`, which is not in the runtime
`FINDING_KINDS`; the adapter's schema-valid `hunt_anomaly` was scored
exact_match 0 for an answer Phantom accepts. The fixture now uses the runtime
kind, and `training/golden_check.py` (new) validates every golden row against
`phantom.automation.ai.schemas` — the same validators the runtime refuses a
model with — so this class of defect cannot come back silently:

```
$ python -m training.golden_check
exploit      OK
finding      OK
osint        OK
social       OK
scan_parse   OK
evolution    OK
```

### social — "not measured, not promoted" with no number at all

`training.eval --phase social` reported 0 by design because no rubric callable
existed. `training/rubric.py` (new) supplies a deterministic one: the
disqualifying tells come from `phantom.automation.social.pretext_score` (the
same scorer the campaign path refuses a draft on) and each golden criterion
maps to one check over the draft plus its row context. A criterion with no
check scores 0 — an unverifiable criterion is not a passed one — and the unmet
list makes a low score auditable.

```
$ python -m training.eval --phase social --predictions training/eval/v3/social.pred.jsonl
score 0.683333  (social-1 0.8, social-2 0.5, social-3 0.75; baseline path: no draft at all = 0.0)
```

An adversarial draft (generic greeting + urgency + invented `bit.ly` link +
password request) scores 0.4 on the same criteria; an empty draft 0.0. The
manifest was NOT promoted: the built-in rubric is a measurement, and the
baseline it beats here is the absence of a generator, which is not a
production bar.

## 8. Known limits / next actions

1. The default best-path mode can stop on a quiet exposure before a CVE fires.
   `--exhaustive` reaches the CVE; a ranking change is a policy decision, not a
   bug fix, and is left to the operator.
2. Auto-mode still cannot deepen a *filtered* host: `version_detect` refuses
   with no known port, which is correct, so a host that opens later needs a new
   run (or the recon ladder's escalation), not a smarter fingerprint.
3. The exploit dataset grew to 113 graded rows from this checkout's own runs.
   Before a production adapter, the labels want runs that *executed* several
   candidates (`--exhaustive` in the lab) so the order reflects measured
   outcomes rather than the planner's priority for the untouched tail.
4. `social` still has no deterministic draft generator to use as a baseline,
   so its manifest stays unpromoted on purpose.
5. No GGUF was exported and no adapter is loaded by the runtime: the training
   path stays offline (`ai.mode` defaults to `off`).
